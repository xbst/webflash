# AGENTS.md

Guidance for AI coding agents working in the WebFlash repository. Human-facing documentation lives in a separate repository, [doctools-docs](https://github.com/xbst/doctools-docs), to be published at <https://doctools.isiks.tech/webflash/>; this repository keeps only a short [`README.md`](README.md). This file covers how the pieces fit together and the conventions to follow when changing them.

## What this project is

WebFlash configures, builds and flashes Klipper, Kalico and Katapult firmware for 3D printer boards from a web browser. It is one tool, **`webflash`**: one command, one distribution, one Python package, with the same shape as [PinConnect](https://github.com/xbst/PinConnect) and [3DStep](https://github.com/xbst/3DStep), whose patterns it copies wherever they apply:

1. **The site** (`src/webflash/site/`): a browser app that configures the firmware with the project's own Kconfig files, compiles it in the browser with clang and lld built to WebAssembly (the `webflash-toolchain` repository), flashes it over WebUSB and Web Serial, and writes board TOMLs. It does not reimplement anything in JavaScript that the package does: it loads the `webflash` package into Pyodide, in a Web Worker, and calls it. `webflash` with no arguments serves it locally; it will be hosted at <https://webflash.isiks.tech>.
2. **The command line** (`webflash board.toml`): reads a board TOML and writes `board.webflash.html`, the embeddable page, for CI pipelines that publish docs sites. Maintainer subcommands (`build`, `make-check`, `inspect`, `parity`, `sources`) run the build engine natively.
3. **The generated page**: a themed card for one board, embedded in MkDocs / Zensical sites with [md-iframe](https://github.com/xbst/md-iframe). It loads the embed runtime from `engine_url` (`https://webflash.isiks.tech/engine/v1/` by default), follows the host's light/dark scheme with PinConnect's theme-sync contract and reports its height with md-iframe's protocol. Until the runtime loads (or without JavaScript) it shows a static fallback card.

The board TOML is the interface between the site and the renderer; the generated HTML is the interface between the renderer and the publishing step.

**Status.** In place: the package core (the board TOML and theme loaders and the TOML writer, the renderer, the command line, the local server, the Pyodide payload, the site's bridge, the bundled themes), the site shell (toolbar, panels, the engine worker with its JSON RPC, Open / Save TOML, the TOML tab, Generate, About), the build engine and the maintainer subcommands (`src/webflash/engine/`), the source snapshots and the Pages deploy (`sources.toml`, `sources.py`, `.github/workflows/pages.yml`), the configure UI (the Project and Version selects over the sources index, the Kconfig tree, the `.config` tab, the Embed options tab, cached downloads in the engine worker), the in-browser build (`site/js/build/`, the toolchain workers), flashing (`site/js/flash/`) and one example per flashing path. Still to come: the embed runtime (`site/js/embed/`, chunk 08), so a generated page shows only its static fallback.

## Repository layout

- `pyproject.toml`: the `webflash` distribution (src layout). Declares one console script, `webflash`. Packages are found under `src/` (`webflash`, and `webflash.engine` once it has an `__init__.py`); package data is listed by file type. `setup.py` clears setuptools' staged `build/lib/webflash` before each build so deleted files never reach a wheel. `MANIFEST.in` keeps a working copy's tests out of the sdist.
- `src/webflash/`: the package.
  - `cli.py`: `main()`, the `webflash` command: no file opens the site, a `.toml` renders, and a first argument naming a maintainer command hands the whole argument list to its module's `main(argv)` (`webflash.engine.cli` for `build`, `make-check`, `inspect` and `parity`; `webflash.sources` for `sources`), which returns an exit code. A command whose module does not exist yet prints `Error: this command is not available yet (chunk NN)`. `__main__.py` makes `python -m webflash` call `main()`.
  - `config.py`: the board TOML dataclasses (`BoardConfig`, `Board`, `Firmware`, `Option`, `Flash`, `Prebuilt`), `load_board`, `parse_defconfig`, `board_data` (the tables, normalized) and `dump_board` (the writer); the theme dataclasses (`Theme`, `ThemeFont`, `ThemeBehavior`), `load_theme` and `theme_path`.
  - `renderer.py`: `render_text` (the text markup), the theme and behavior CSS, the theme-sync and height scripts, `config_json`, `site_url`, `toml_fragment`, `generate_html`, and `build_page`, the one sequence (load, theme, inline assets, render) that both the command line and the bridge run.
  - `serve.py`: the local server (the site at `/`, the embed runtime at `/engine/v1/`, the `--assets` folder at `/toolchain/` and `/sources/`, the payload rebuilt when a request finds it stale). `payload.py`: locates the site (`site_root()`) and builds the Pyodide payload; `python -m webflash.payload [--force]` builds it by hand.
  - `themes/`: theme definitions (`*.toml`). **Source of truth** for themes, read by the site through the bridge.
  - `site/`: the site (vanilla ES modules, no framework, no bundler): `index.html`, `css/style.css`, `js/main.js` wires `state.js` (the session: the board TOML's tables with undo, the TOML text derived from them, the sources index, the ref being configured, the `.config`, the Kconfig tree, the build plan, the files opened with the TOML), `toml-io.js` (the TOML parser, the comment-keeping patcher, the writer, the `#toml=` codec), `dialogs.js` (Generate, About, errors), `runtime.js` (the engine worker's RPC) and `js/configure/` (`sources.js` the index and what a version names, `version-picker.js` the toolbar's Project and Version, `configurator.js` the engine side of configuring, `kconfig-tree.js` the tree, `config-tab.js` the `.config` tab, `options-panel.js` the Embed options tab); `js/build/` (`build-panel.js` the Build card, `toolchain-pool.js` the toolchain workers and the job queue, `cache.js` the checked toolchain downloads and the storage estimate, `artifacts.js` the files and `session.build`, `tar.js` the bundle reader) and `js/flash/` (the Flash card and the protocols); `js/workers/engine-worker.js` runs Pyodide, `js/workers/toolchain-worker.js` runs one WebAssembly LLVM, and `js/workers/blob-cache.js` holds the cached downloads; `py/bridge.py` is the only Python the site adds. Chunk 08 adds `js/embed/`.
  - `site/webflash.zip`: the payload the engine worker fetches. **Generated and git-ignored.**
- `examples/<name>/<name>.toml`: one board TOML per flashing path (`stm32g0b1-usb` with a placeholder photo, `rp2040-usb`, `rp2040-katapult`, `can-toolhead`, `katapult-stm32g0b1`, `lpc1769`, `prebuilt`). Their defconfigs are `make savedefconfig` output from Klipper and Katapult `master` (late October 2026), so each TOML's comment says which defaults the short defconfig relies on. `examples/prebuilt/katapult.bin` is added only from a build verified on hardware (see its README).

## Key facts and gotchas

- **The site must be served over HTTP.** Its engine worker fetches `webflash.zip`, so opening `index.html` via `file://` fails. Run `webflash`, which builds the payload, picks a free port and opens a browser. Serving the folder by hand needs `python -m webflash.payload` first (in a source checkout; an installed copy needs `python -m webflash.payload <site folder>/webflash.zip`, since its default is the user cache).
- **Python runs in a Web Worker, booted on first need.** `runtime.js` starts `workers/engine-worker.js` (a module worker) on the first `call()`, not at page load: loading a version in the Configure tab (a first visit asks first, showing the download sizes; later visits load at once), opening a TOML, Generate, the theme list, or a `#toml=` / `?config=` link boots it. The worker loads Pyodide from jsDelivr (`PYODIDE_VERSION`, pinned in both `runtime.js` and `engine-worker.js`, in step with PinConnect), fetches the payload from the `payloadUrl` its `boot` message names (the caller resolves it, since generated pages load the same worker from `/engine/v1/workers/`), and extracts it with Python's `zipfile`. Messages are `{id, method, params, long?}` in and `{id, result}` or `{id, error}` out, plus `{progress: {phase, detail, done?, total?, call?}}` (`done` and `total` count steps or bytes, `call` is the id of the call it belongs to); `{cancel: id}` asks a call sent with `long: true` to stop. Every method other than `boot` is the worker's own (`fetchBlob`, `loadSources`: downloads) or a function of `bridge.py` called with `params` as its positional arguments (typed arrays arrive as Python `bytes`; an async function is awaited). Python reports progress through the `webflash_js` module the worker registers, `progress(phase, detail, done=None, total=None)`, and polls `cancelled()` between the steps of a long call: a cancel can only land while Python awaits. `runtime.call(method, params, {onProgress, signal, long, early})` routes a call's own progress to it and cancels through an `AbortSignal`. `runtime.pythonMessage` keeps a Python error's last line, as PinConnect's does.
- **Downloads go through Cache Storage when their URL names their content.** `workers/blob-cache.js` (`fetchBlob`, `isCached`, `clearCache`, `gunzip`; importable from any worker and the page) keeps `sources/blobs/<sha256>.tar.gz` (checked against the SHA-256 in its name before it is kept) and `toolchain/<id>/...` in the `webflash-v1` cache forever, and fetches everything else (`sources/index.json`, `toolchain/current.json`) with `cache: "no-cache"`. About's Clear cache empties it. A core bundle reaches Python uncompressed: the worker gunzips it with `DecompressionStream` and hands the tar to `bridge.load_sources`.
- **The site's Generate matches the command line byte for byte.** Both call `renderer.build_page` on the same files: the bridge writes the TOML to `/webflash/work/board.toml` (as bytes, so a CRLF text stays CRLF until the loader normalizes it) and the image and prebuilt file beside it under the names the TOML gives them, then renders. Everything in the output must be deterministic: `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=True)` for the config JSON, no timestamps, random values, platform, absolute paths or environment (the version comes from `__version__`), a fixed media-type table rather than `mimetypes` (which reads the Windows registry), no compression, and LF newlines (the CLI writes with `newline="\n"`; `config.read_text` drops a BOM and turns CRLF into LF).
- **The page is assembled by token replacement, not `str.format`.** `@@NAME@@` tokens in `_HTML_TEMPLATE` are replaced in one pass, so the inlined CSS and JavaScript need no brace escaping and nothing inserted is scanned again. Every string from the TOML that lands in HTML is escaped; the config JSON escapes `<`, `>` and `&`; inlined scripts and styles have `</script` / `</style` neutralized.
- **The page's parts.** The theme's CSS variables (`--bg`, `--accent`, `--log-bg`, ...: every `[colors.*]` token, plus `--ui-font`, `--mono-font`, `--font-scale`, `--max-width`), the fallback card's CSS, PinConnect's theme-sync script verbatim, the card root `<div class="wf-card" id="wf-card">` with a `data-*` attribute for every behavior key (`show_log` is `data-show-log`, booleans are `"true"` / `"false"`), the static fallback inside it (title, description, photo, and either the "Chrome or Edge" sentence linking the site with `#toml=`, or the prebuilt file's download link), `<script type="application/json" id="webflash-config">` (the tables of `board_data`, `schema: 1`, plus `inline: {image, prebuilt}` data URLs with `-i`), the height script, and `<script type="module" src="<engine_url>embed.js">`. The embed runtime (chunk 08) reads the JSON and replaces the fallback; until then a generated page logs one failed load, of `embed.js`.
- **The color scheme is `data-theme` on `<html>`**, set by PinConnect's theme-sync script verbatim: `?theme=dark|light`, a `{pinconnectTheme: "dark"|"light"}` message (the key is PinConnect's on purpose, so one host script drives every tool), or the same-origin parent's `data-md-color-scheme` / `data-theme` / `dark` class, tracked live; else `prefers-color-scheme`. The theme CSS keys its palettes on it. The site sets `data-theme` on its own `<html>` too (dark unless the system asks for light, or `?theme=`), so the Generate preview, a same-origin `srcdoc` frame, follows the site.
- **The page reports its height** as `{mdIframeHeight: h}` (`document.body.scrollHeight`, rounded up) whenever the card's size changes (a `ResizeObserver` on `#wf-card`, `load`, `resize`, and a `webflash-relayout` event the runtime fires for anything else), only when embedded, never 0, and hides its own scrollbar when embedded, as 3DStep's pages do. The Generate preview applies the same message to its frame.
- **"Open in WebFlash" is `#toml=`** plus the TOML text as base64url (RFC 4648 section 5, no padding) of its UTF-8 bytes, LF newlines: `renderer.toml_fragment` writes it, `toml-io.js`'s `tomlFromHash` reads it, and the site opens it at load and on `hashchange`. The link goes to `site_url(engine_url)`: the engine URL with its `engine/vN/` folder taken off, else the origin's root. `?config=<url>` opens a TOML from a URL that allows CORS; `?project=` and `?version=` preselect.
- **`engine_url` and the local server.** `/engine/v1/` holds `site/js/embed/*` at its root and `flash/`, `build/`, `workers/` and `css/` beside it (from `site/js/flash/` and so on), so modules in `js/embed/` import `./flash/...` and only ever run from `/engine/v1/`; the Pages deploy must stage the same layout. A board TOML with `engine_url = "http://127.0.0.1:<port>/engine/v1/"` renders a page that runs against `webflash --port <port>`. The server sends `Access-Control-Allow-Origin: *` on everything, as GitHub Pages does, so a page served elsewhere can load it.
- **Where the toolchain and the sources come from.** `index.html` carries a `<!--webflash-assets-->` placeholder that the local server replaces with `<meta name="webflash-assets" content="<url>">`: the `--assets` URL (default `https://webflash.isiks.tech/`), or empty for an `--assets` folder, which the server then serves at `/toolchain/` and `/sources/`. The hosted site ships the placeholder untouched, so there is no tag and the page uses its own origin. `runtime.assetsBase()` reads it.
- **The board TOML is strict, themes are lenient.** Unknown keys and tables in a board TOML are errors, and so are wrong types, unknown projects and methods, a `[firmware]` / `[config]` / `[prebuilt]` mix, a defconfig line that is not `.config` syntax or sets a symbol twice, a `.bin` without `address` and any other file with one. Errors read `<file>: <table>: <message>`. Warnings (a label for a value not offered, instructions for a method not offered) are collected on `BoardConfig.warnings`. The loader never checks symbols against a Kconfig or versions against the sources index: the site does that once it has them. Theme files warn about unknown `[behavior]` keys and tables, pass unknown color tokens through as CSS variables, fix a bare hex color with a warning, and clamp `font_scale` (0.5 to 3) and `max_width` (at least 280).
- **Two TOML writers write the same text.** `config.dump_board` (behind `bridge.save_toml`) and `toml-io.js`'s `writeBoardToml` write a fresh board TOML from `board_data`'s tables, in the order of the board TOML reference, leaving out keys that hold their default (except `[firmware] version`). Option `labels` follow the order of `values`, then any other keys sorted: a JavaScript object cannot keep the TOML's order for integer-like keys such as `500000`. Change both writers together; the local JS tests compare them.
- **The session holds the board TOML's tables; the TOML is written from them.** Open TOML (and `#toml=`, `?config=`) checks the text with `bridge.check_board`, puts its `board` tables (`board_data`'s shape) into the session and loads its project and version with its defconfig; Configure, Embed options and the toolbar change the tables; the TOML tab shows, read-only, what Save TOML writes (`bridge.save_toml` when Python is up, else `toml-io.js`'s `writeBoardToml`, the same text), so an opened TOML's comments are not kept. `[config] defconfig` is the engine's `kconfig_defconfig()` once a version is loaded, the opened text before. The Theme selects (the toolbar's, Embed options' and Generate's) set `[board] theme`, so the downloaded TOML renders to the downloaded page with the command line too. Generate's `-i` is enabled only when every file the TOML names was opened with it. Undo and redo cover the tables; restoring one reloads its defconfig into the engine.
- **Configuring a version.** `sources/index.json` (from the assets origin, revalidated) lists each project's refs: the default branch, tags newest first, other branches. `[firmware] version` is `latest` (the default branch's snapshot when its `checked` is true, else the newest checked ref, else the default branch, badged), `release` (the newest checked tag) or a ref id; a ref whose `checked` is false or null is badged "unchecked" and never chosen by those two. The Configure tab loads the chosen ref's core bundle (sizes from the index's `blobs` table are shown before the first download; later visits load at once from the cache), runs `kconfig_load` with the session's defconfig, and renders `kconfig_tree()` (chunk 03's `{root: [ids], nodes, title}`, normalized by `kconfig-tree.js`'s `normalizeTree`) as menuconfig shows it, patched by node id after each `kconfig_set`. Switching project or version carries the defconfig over, plus the selected `MACH_` architecture and processor where the defconfig leaves them to the defaults (the projects default to different chips), and lists the symbols the new version lacks and the values it would not take. Every engine call runs in order through `configurator.js`'s queue: the engine holds one tree. A bundle that answers 404 (an old snapshot of a moved branch) makes the page reload the index once.
- **The build runs in toolchain workers.** Build reads `toolchain/current.json` (revalidated) and `toolchain/<id>/manifest.json`, loads the release's `llvm.js`, `llvm.wasm.gz`, `toolchain.js` and `sysroot.tar.gz` through Cache Storage, each checked against the manifest's size and SHA-256 (a copy that fails is dropped and fetched again), and starts N `workers/toolchain-worker.js` module workers: one per core but one, at most 4, halved below 8 GB of `navigator.deviceMemory`, or what About sets (`localStorage` `webflash.build.workers`). Each worker gets the bytes, imports `toolchain.js` and `llvm.js` from Blob URLs of them (so a repeat visit fetches nothing; Node falls back to the files' URLs), compiles the module once, and mounts the core and lib bundles at the engine's own tree path (`/webflash/src/<project>/<sha>`). The page hands one `MessagePort` per worker to the engine worker (`attachToolchain`), whose `webflash_js.run_tool(spec_json, files)` (the engine's `JsToolchain` hook) queues each job for the next free worker, the job's files transferred; a worker runs one job at a time, creates the folders the outputs go to (the tools create none; MEMFS resolves `..` from the folder it has reached, so `out/src/../lib/x.o` needs `out/src` too) and answers every file the tool wrote. The build runs inside `configurator.exclusive()` with configuring locked; Cancel aborts the call, fails the queued jobs (`detachToolchain`) and terminates the workers, which start again with the next build. A first visit lists the downloads with sizes and waits for a click (`localStorage` `webflash.build.auto` afterwards). The result goes to `session.build` (`{project, ref, version, config, outputs: Map, appAddress, mcu, ...}`; `appAddress` is `CONFIG_FLASH_START` for Katapult) with a `change` event `"build"`.
- **The payload holds `bridge.py` at its root and the package under `webflash/`**: every `.py` and `.toml` except the site and the server-side modules (`cli.py`, `serve.py`, `payload.py`, `sources.py`, `__main__.py`). The zip's comment is a digest of every member's name and bytes, and `payload_is_stale` compares it rather than mtimes. It is built beside the site in a source checkout and in the per-user cache (`<cache>/webflash/<hash of the package path>/`) for an installed package, exactly as PinConnect's. A running `webflash` rebuilds a stale payload when the site asks for it, under one lock, served from memory; only an edit to `serve.py` or `payload.py` needs a restart.
- **Package data is listed by file type** in `pyproject.toml` (`site/js/*.js`, `site/js/*/*.js` and so on), not with a recursive glob: older setuptools releases do not expand `**`, and the explicit list keeps the payload zip and bytecode caches out of the wheel. A new kind of file (a new folder depth or extension, such as `.wasm` or `.mjs`) needs a line there.

## Common commands

Install for development and run the site (Python 3.9+):

```bash
pip install -e .
webflash                       # builds the payload, picks a port, opens a browser
webflash --port 8000 --no-browser
webflash --assets ./local-assets   # serve toolchain/ and sources/ from a folder
```

Render a board TOML:

```bash
webflash examples/stm32g0b1-usb/stm32g0b1-usb.toml          # writes examples/stm32g0b1-usb/stm32g0b1-usb.webflash.html
webflash examples/can-toolhead/can-toolhead.toml -t slate -i -o can.html
```

Build the site's payload by hand (only needed to serve `src/webflash/site/` some other way):

```bash
python -m webflash.payload --force
```

## Documentation

The docs will live in [doctools-docs](https://github.com/xbst/doctools-docs) (a sibling checkout, `..\doctools-docs`), the Zensical site shared with PinConnect, 3DStep and md-iframe, under `docs/webflash/`. Topics shared by every tool (publishing from CI, light and dark mode) are under its `docs/guides/`.

- **A behavior change here usually needs a docs change there.** Make it in doctools-docs in step with the code change, as a commit in that repository, and mention it in this one's commit message. The board TOML and theme references follow `config.py`; the generated page's reference follows `renderer.py` and the embed runtime; the command line page follows `cli.py`.

## Conventions

- **Docs use one line per paragraph.** GitHub's Markdown viewer soft-wraps, so do not hard-wrap prose in the README, this file or doctools-docs.
- **Code, comments and docs are US English.** Prose uses `colors`, `behaviors`, `gray`, `labeled`, matching the TOML keys users type.
- **Commit messages** are a short imperative sentence ("Add the Kconfig tree", "Fix the DFU erase loop"), no conventional-commit prefixes.
- **Generated and ephemeral files are git-ignored** through a local-only `.gitignore` (it ignores itself, as in PinConnect and 3DStep, so a fresh clone or worktree has none: copy it in). Never commit `*.webflash.html`, `src/webflash/site/webflash.zip`, `tests/`, `plans/`, `venv/` or `.claude/`.
- **No new runtime dependencies without reason.** `webflash` relies only on the standard library (`tomllib`, with a `tomli` fallback below 3.11); the site is dependency-free vanilla JS at runtime apart from Pyodide from a CDN and, later, the toolchain release.

## Verifying changes

- After editing `renderer.py`, `config.py` or a theme, render the examples and open the HTML over HTTP (`python -m http.server` in a folder holding the page and its photo), standalone and in light and dark (`?theme=dark`), and at 375 px. The console should show one error, the failed load of `embed.js` from `webflash.isiks.tech`, until the embed runtime and the deploy exist.
- After editing anything in the package (a theme, the bridge, the renderer), reload the site (a running `webflash` rebuilds its payload; restart it only after changing `serve.py` or `payload.py`) and confirm Generate still works. An example's Generate in the site must give the same bytes as `webflash` on the same TOML, with and without `-i`.
- After changing packaging, build a wheel (`python -m build`) and list it: it should hold exactly `webflash/**` plus metadata, with no zip and no tests.
- **Tests are not committed** (`tests/` and `test_*.py` are git-ignored), so a fresh clone has none. A working copy may still have `tests/`: if they are present, run `python -m pytest tests` and `node --no-warnings --test "tests/js/*.test.mjs"` (Node 24 does not expand a bare directory) before finishing, and add cases for new behavior. Never `git add` a test file.
