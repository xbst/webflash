# AGENTS.md

Guidance for AI coding agents working in the WebFlash repository. Human-facing documentation lives in a separate repository, [doctools-docs](https://github.com/xbst/doctools-docs), to be published at <https://doctools.isiks.tech/webflash/>; this repository keeps only a short [`README.md`](README.md). This file covers how the pieces fit together and the conventions to follow when changing them.

## What this project is

WebFlash configures, builds and flashes Klipper, Kalico and Katapult firmware for 3D printer boards from a web browser. It is one tool, **`webflash`**: one command, one distribution, one Python package, with the same shape as [PinConnect](https://github.com/xbst/PinConnect) and [3DStep](https://github.com/xbst/3DStep), whose patterns it copies wherever they apply:

1. **The site** (`src/webflash/site/`): a browser app that configures the firmware with the project's own Kconfig files, compiles it in the browser with clang and lld built to WebAssembly (the `webflash-toolchain` repository), flashes it over WebUSB and Web Serial, and writes board TOMLs. It does not reimplement anything in JavaScript that the package does: it loads the `webflash` package into Pyodide, in a Web Worker, and calls it. `webflash` with no arguments serves it locally; it will be hosted at <https://webflash.isiks.tech>.
2. **The command line** (`webflash board.toml`): reads a board TOML and writes `board.webflash.html`, the embeddable page, for CI pipelines that publish docs sites. Maintainer subcommands (`build`, `make-check`, `inspect`, `parity`, `sources`) run the build engine natively.
3. **The generated page**: a themed card for one board, embedded in MkDocs / Zensical sites with [md-iframe](https://github.com/xbst/md-iframe). It loads the embed runtime from `engine_url` (`https://webflash.isiks.tech/engine/v1/` by default), follows the host's light/dark scheme with PinConnect's theme-sync contract and reports its height with md-iframe's protocol. Until the runtime loads (or without JavaScript) it shows a static fallback card.

The board TOML is the interface between the site and the renderer; the generated HTML is the interface between the renderer and the publishing step.

**Status.** Everything v1 needs is in place and has run end to end on real boards (`tools/parity/hardware.md`): the package core (the board TOML and theme loaders and the TOML writer, the renderer, the command line, the local server, the Pyodide payload, the site's bridge, the bundled themes), the site (a guided wizard of five steps, Firmware, Configure, Build, Flash and Embed; the engine worker with its JSON RPC, Open / Save TOML, the TOML tab, Generate with its live preview, About), Klipper or Kalico configured, built and flashed together with Katapult (two engine slots, the options both use set once), older commits of the default branch as versions (labeled by `git describe`, as Mainsail shows them), board TOMLs with several setups (`[[setup]]`) and `[katapult]`, the build engine and the maintainer subcommands (`src/webflash/engine/`), the source snapshots with their gate and the Pages deploy (`sources.toml`, `sources.py`, `.github/workflows/pages.yml`), the configure UI, the in-browser build (`site/js/build/`, the toolchain workers), flashing (`site/js/flash/`: STM32 DFU, RP2040/RP2350 PICOBOOT and UF2, Katapult over USB, UART and CAN), the embed runtime (`site/js/embed/`, the same steps in the card), and one example per flashing path. What waits is the release: the first deploy of the site (the toolchain release is copied in through a `TOOLCHAIN_TOKEN` secret while `webflash-toolchain` is private) and the documentation in doctools-docs.

## Repository layout

- `pyproject.toml`: the `webflash` distribution (src layout). Declares one console script, `webflash`. Packages are found under `src/` (`webflash` and `webflash.engine`); package data is listed by file type. `setup.py` clears setuptools' staged `build/lib/webflash` before each build so deleted files never reach a wheel. `MANIFEST.in` keeps a working copy's tests out of the sdist.
- `src/webflash/`: the package.
  - `cli.py`: `main()`, the `webflash` command: no file opens the site, a `.toml` renders, and a first argument naming a maintainer command hands the whole argument list to its module's `main(argv)` (`webflash.engine.cli` for `build`, `make-check`, `inspect` and `parity`; `webflash.sources` for `sources`), which returns an exit code. An installation without that module prints `Error: this installation of webflash has no <module>, which runs this command`. `__main__.py` makes `python -m webflash` call `main()`.
  - `config.py`: the board TOML dataclasses (`BoardConfig`, `Board`, `Firmware`, `Option`, `Flash`, `Prebuilt`), `load_board`, `parse_defconfig`, `board_data` (the tables, normalized) and `dump_board` (the writer); the theme dataclasses (`Theme`, `ThemeFont`, `ThemeBehavior`), `load_theme` and `theme_path`.
  - `renderer.py`: `render_text` (the text markup), the theme and behavior CSS, the theme-sync and height scripts, `config_json`, `site_url`, `toml_fragment`, `generate_html`, and `build_page`, the one sequence (load, theme, inline assets, render) that both the command line and the bridge run.
  - `serve.py`: the local server (the site at `/`, the embed runtime at `/engine/v1/`, the `toolchain/` and `sources/` folders of the `--assets` folder at `/toolchain/` and `/sources/`, nothing else of it, the payload rebuilt when a request finds it stale). `payload.py`: locates the site (`site_root()`) and builds the Pyodide payload; `python -m webflash.payload [--force]` builds it by hand.
  - `sources.py`: `webflash sources build|index|check`, the source snapshots: each project's refs (by `sources.toml`) cloned, cut into a core bundle and one bundle per `lib/<dir>` (plain ustar in gzip, named by the SHA-256 of their bytes, shared across refs and projects by git tree id), gated, and listed in `sources/index.json`; the older commits of the default branch (`history_days`) are snapshotted the same way and listed apart, in `sources/history/<project>.json` (a commit a listed ref holds, such as a release tagged on the default branch, is listed only as that ref); a `--ref` run rebuilds only the refs it names, leaves the history alone and ages out nothing; a run that finds the upstream tags changed describes every cached snapshot again, abbreviation included (`refresh_describes`; the gate reports keep the label they built with), since a tag placed on a commit already snapshotted changes the label of that commit and of every commit after it.
  - `engine/`: the build engine. `make.py` (the GNU make interpreter; `$(info)` lands in its transcript beside the echoed commands, `$(warning)` in the log), `shell.py` (the recipes' shell commands), `pyrun.py` (the project's own Python scripts, in process, behind a `subprocess.Popen` shim), `kconfig.py` (`Session` over the tree's own kconfiglib: the tree JSON, set, `.config`, defconfig; node ids carry a prefix, the slot), `pair.py` (a firmware and Katapult side by side: the options both define, mirrored from one to the other, and Klipper's bootloader offset linked to Katapult's application offset), `driver.py` (GCC command lines turned into clang, `ld.lld` and `llvm-objcopy` ones, soft-float as GCC builds and with `--entry=ResetHandler` on the firmware links, with the compatibility copies the projects' sources need), `toolchain.py` (`NativeToolchain` for GCC or ATfE's clang, `JsToolchain` for the browser, `WasmNodeToolchain` for the release under Node), `build.py` (`Build`: `.config`, the Arm-only check, the version, `make all` in waves, the outputs and the memory table), `uf2.py` (elf2uf2, with the family the `.config` calls for), `inspect.py` (ELF, bin, hex and UF2 summaries; a truncated or malformed file is an `InspectError`, never a traceback), `methods.py` (the flashing methods a configuration allows and the architectures WebFlash cannot build, the twin of `devices.js`'s `inferMethods` and `unsupportedReason`) and `cli.py` (`build`, `make-check`, `inspect`, `parity`).
  - `themes/`: theme definitions (`*.toml`). **Source of truth** for themes, read by the site through the bridge.
  - `site/`: the site (vanilla ES modules, no framework, no bundler): `index.html`, `css/style.css`, `js/main.js` wires `state.js` (the session: the board TOML's tables with undo, the TOML text derived from them, the sources index, the setup being edited, the ref being configured, the `.config`, the Kconfig tree, Katapult's part beside them, the build plan, the builds, the files opened with the TOML), `toml-io.js` (the TOML parser, the comment-keeping patcher, the writer, the `#toml=` codec), `dialogs.js` (Generate, About, errors: one stack of modals, the page behind them inert, Escape closing the topmost), `runtime.js` (the engine worker's RPC), `js/wizard/` (`wizard.js` the steps, the step bar and their browser history, `firmware-page.js` page 1, `status-chip.js` the top bar's status chip) and `js/configure/` (`sources.js` the index, the older commits and what a version names, `version-picker.js` the searchable version picker, `configurator.js` the engine side of configuring, both slots, `configure-page.js` the Configure step, `kconfig-tree.js` the tree, `config-tab.js` the `.config` tab, `options-panel.js` the Embed options tab, `setups.js` the setups editor's table work, `open-config.js` Open .config's reading of the files); `js/build/` (`build-panel.js` the Build step, `builder.js` one build or a pair, `toolchain-pool.js` the toolchain workers and the job queue, `cache.js` the checked toolchain downloads and the storage estimate, `artifacts.js` the files and `session.builds`, `tar.js` the bundle reader) and `js/flash/` (the Flash step and the protocols; `pair.js` the firmware object for Katapult and Klipper together); `js/workers/engine-worker.js` runs Pyodide, `js/workers/toolchain-worker.js` runs one WebAssembly LLVM, and `js/workers/blob-cache.js` holds the cached downloads; `py/bridge.py` is the only Python the site adds. `js/embed/` is the runtime generated pages load from `/engine/v1/`: `embed.js` (the entry: the config JSON, where the runtime's site is, the stylesheet `css/embed.css`), `embed-ui.js` (the card's steps, the flash panel, the notices, the `[prebuilt]` flow), `embed-build.js` (`FirmwareFlow`: page 1's picks, the Setup step, Build; loaded only for a board built from source) and `embed-model.js` (what needs no DOM, tested under Node).
  - `site/webflash.zip`: the payload the engine worker fetches. **Generated and git-ignored.**
- `examples/<name>/<name>.toml`: one board TOML per flashing path (`stm32g0b1-usb` with a placeholder photo and `[katapult]`, unticked when the card opens, `rp2040-usb`, `rp2040-katapult`, `can-toolhead` with two setups, CAN with Katapult and USB without, `katapult-stm32g0b1`, `lpc1769`, `prebuilt`). Their defconfigs are `make savedefconfig` output from Klipper and Katapult `master` (late October 2026), so each TOML's comment says which defaults the short defconfig relies on. `examples/prebuilt/katapult.bin` is the site's own build of `examples/katapult-stm32g0b1`, flashed and verified on a board; its README says how it was made. Replace it only with a build checked the same way.
- `sources.toml`: the snapshot policy: each project's repository and refs (the default branch and the newest tags), how far back its older commits go (`history_days`, optionally `history_max`; Klipper and Kalico 365 days, Katapult 730) and how they are gated (`history_gate`, `full` or `reduced`), what the core bundle holds, the pruning rules for the lib bundles, and how long a ref or an older commit that left the policy stays listed.
- `tools/parity/`: `matrix.toml` (one row per MCU family and flashing path, each a defconfig and optionally `unless`, symbols whose presence in a tree's Kconfig makes the row not apply: what `ci.yml`, the snapshot gate and `webflash parity` build), `README.md` (what the parity checks compare), `wasm-node-runner.mjs` (the release's WebAssembly tools under Node, for `--toolchain wasm-node`) and `hardware.md` (the checklist for real boards, with every result so far).
- `.github/workflows/`: `ci.yml` (on Ubuntu: `make-check` and `parity` over the matrix, the C++ elf2uf2 against `uf2.py` (byte for byte with Klipper's RP2040 family; the engine's RP2350 `.uf2` differs on purpose in each block's family field), a real `make` build compared byte for byte with the engine's) and `pages.yml` (stages the site, copies in the latest toolchain release, builds and gates the snapshots, checks the staged site, deploys `master`).

## Key facts and gotchas

- **The site must be served over HTTP.** Its engine worker fetches `webflash.zip`, so opening `index.html` via `file://` fails. Run `webflash`, which builds the payload, picks a free port and opens a browser. Serving the folder by hand needs `python -m webflash.payload` first (in a source checkout; an installed copy needs `python -m webflash.payload <site folder>/webflash.zip`, since its default is the user cache).
- **Python runs in a Web Worker, booted on first need.** `runtime.js` starts `workers/engine-worker.js` (a module worker) on the first `call()`, not at page load: Next on page 1 (the step's hint names what it downloads and its size; a returning visitor's configuration loads at once, `webflash.configure.auto`), opening a TOML, Generate, the theme list, or a `#toml=` / `?config=` link boots it. A failed boot is kept, so the calls waiting on it fail with its error; the next call made after it (Try again, a card's Next or Build, Generate) starts a fresh worker and boots again, as Try again on Python's row in the status chip's popover does. The worker loads Pyodide from jsDelivr (`PYODIDE_VERSION`, pinned in both `runtime.js` and `engine-worker.js`, in step with PinConnect), fetches the payload from the `payloadUrl` its `boot` message names (the caller resolves it, since generated pages load the same worker from `/engine/v1/workers/`; its `embedded` flag, set by `runtime.js` once `configure()` named a payload, makes a failed payload download read as the WebFlash site being unreachable rather than as advice for whoever serves the site), and extracts it with Python's `zipfile`. Messages are `{id, method, params, long?}` in and `{id, result}` or `{id, error}` out, plus `{progress: {phase, detail, done?, total?, call?}}` (`done` and `total` count steps or bytes, `call` is the id of the call it belongs to); `{cancel: id}` asks a call sent with `long: true` to stop. Every method other than `boot` is the worker's own (`fetchBlob`, `loadSources`: downloads) or a function of `bridge.py` called with `params` as its positional arguments (typed arrays arrive as Python `bytes`; an async function is awaited). Python reports progress through the `webflash_js` module the worker registers, `progress(phase, detail, done=None, total=None)`, and polls `cancelled()` between the steps of a long call: a cancel can only land while Python awaits. `runtime.call(method, params, {onProgress, signal, long, early})` routes a call's own progress to it and cancels through an `AbortSignal`. `runtime.pythonMessage` keeps the final exception's whole message (every line, without the class name and the frames; a chained traceback gives the last exception's) and returns text that does not start with a traceback as it is. A generated page runs the same module from another site: it calls `runtime.configure({assetsBase, payloadUrl})` first, and the worker starts through `toolchain-pool.js`'s `startWorker`, which wraps a script from another origin in a same-origin Blob that imports it (a worker inside such a Blob has a `blob:` location, so every URL it fetches is absolute).
- **Downloads go through Cache Storage when their URL names their content.** `workers/blob-cache.js` (`fetchBlob`, `isCached`, `clearCache`, `gunzip`; importable from any worker and the page) keeps `sources/blobs/<sha256>.tar.gz` (checked against the SHA-256 in its name before it is kept) and `toolchain/<id>/...` in the `webflash-v1` cache forever, and fetches everything else (`sources/index.json`, `toolchain/current.json`) with `cache: "no-cache"`. About's Clear cache empties it. A core bundle reaches Python uncompressed: the worker gunzips it with `DecompressionStream` and hands the tar to `bridge.load_sources`.
- **The site's Generate matches the command line byte for byte.** Both call `renderer.build_page` on the same files: the bridge writes the TOML to `/webflash/work/board.toml` (as bytes, so a CRLF text stays CRLF until the loader normalizes it) and the image and prebuilt file beside it under the names the TOML gives them, then renders. Everything in the output must be deterministic: `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=True)` for the config JSON, no timestamps, random values, platform, absolute paths or environment (the version comes from `__version__`), a fixed media-type table rather than `mimetypes` (which reads the Windows registry), no compression, and LF newlines (the CLI writes with `newline="\n"`; `config.read_text` drops a BOM and turns CRLF into LF).
- **The page is assembled by token replacement, not `str.format`.** `@@NAME@@` tokens in `_HTML_TEMPLATE` are replaced in one pass, so the inlined CSS and JavaScript need no brace escaping and nothing inserted is scanned again. Every string from the TOML that lands in HTML is escaped; the config JSON escapes `<`, `>` and `&`; inlined scripts and styles have `</script` / `</style` neutralized.
- **The page's parts.** The theme's CSS variables (`--bg`, `--accent`, `--log-bg`, ...: every `[colors.*]` token, plus `--ui-font`, `--mono-font`, `--font-scale`, `--max-width`), the fallback card's CSS, PinConnect's theme-sync script verbatim, the card root `<div class="wf-card" id="wf-card">` with a `data-*` attribute for every behavior key (`show_log` is `data-show-log`, booleans are `"true"` / `"false"`), the static fallback inside it (title, description, photo, and either the "Chrome or Edge" sentence linking the site with `#toml=`, naming the first setup when it has a title, or the prebuilt file's download link), `<script type="application/json" id="webflash-config">` (`renderer.page_config`: the tables of `board_data` (`setups`, `setups_form` and `katapult` among them), `schema: 1`, `toml` the TOML's text, and with `-i` on a `[prebuilt]` board `inline: {prebuilt}`, a data URL; an inlined image is only in the fallback's `<img>`, which the runtime keeps), the height script, and `<script type="module" src="<engine_url>embed.js">`. The runtime reads the JSON (a newer `schema` keeps the fallback with a note) and replaces the fallback with the card.
- **The color scheme is `data-theme` on `<html>`**, set by PinConnect's theme-sync script verbatim: `?theme=dark|light`, a `{pinconnectTheme: "dark"|"light"}` message (the key is PinConnect's on purpose, so one host script drives every tool), or the same-origin parent's `data-md-color-scheme` / `data-theme` / `dark` class, tracked live; else `prefers-color-scheme`. The theme CSS keys its palettes on it. The site sets `data-theme` on its own `<html>` too (dark unless the system asks for light, or `?theme=`), so the Generate preview, a same-origin `srcdoc` frame, follows the site.
- **The page reports its height** as `{mdIframeHeight: h}` (`document.body.scrollHeight`, rounded up) whenever the card's size changes (a `ResizeObserver` on `#wf-card`, `load`, `resize`, and a `webflash-relayout` event the runtime fires for anything else), only when embedded, never 0 (the runtime's own relayouts start once the card has replaced the fallback), and hides its own scrollbar when embedded, as 3DStep's pages do. The Generate preview applies the same message to its frame.
- **"Open in WebFlash" is `#toml=`** plus the TOML text as base64url (RFC 4648 section 5, no padding) of its UTF-8 bytes, LF newlines: `renderer.toml_fragment` writes it, `toml-io.js`'s `tomlFromHash` reads it (standard base64 too, padded or not and with `+` and `/` percent-encoded or not; any other character is refused rather than cutting the TOML short), and the site opens it at load and on `hashchange` (main.js's `onHashChange`: not again for the link the board came from, so the browser's Back and Forward across its entry only move between steps, and after asking when another link would replace unsaved changes: one question at a time, answered for the link the address names by then). The link goes to `site_url(engine_url)`: the engine URL with a trailing `engine/vN/` taken off as whole path segments (a host named `engine` is left alone), else the origin's root. `?config=<url>` opens a TOML from a URL that allows CORS; `?project=` and `?version=` preselect.
- **`engine_url` and the local server.** `/engine/v1/` holds `site/js/embed/*` at its root, beside the modules of `site/js/` the build's flow imports (`runtime.js`, `state.js`, `toml-io.js`, `dialogs.js`), and `flash/`, `build/`, `configure/`, `workers/`, `wizard/` and `css/` (from `site/js/flash/` and so on), so modules in `js/embed/` import `./flash/...` and `./runtime.js` and only ever run from `/engine/v1/`, while every other module keeps the imports it has on the site. `serve.py`'s `engine_files(site)` is that layout: the local server serves it, and `pages.yml` stages it with `stage_engine`, then checks that every module reachable from `embed.js` (static imports and `import("...")`) is staged. A module of `js/` that the runtime starts importing needs a line in `_ENGINE_SHARED`. A board TOML with `engine_url = "http://127.0.0.1:<port>/engine/v1/"` renders a page that runs against `webflash --port <port>`; with an `--assets` URL the server writes it into `embed.js` (its `"" /* webflash-assets */` placeholder), else the runtime takes `toolchain/` and `sources/` from its own site (`toml-io.js`'s `siteUrl`, the twin of `renderer.site_url`). The server sends `Access-Control-Allow-Origin: *` on everything, as GitHub Pages does, so a page served elsewhere can load it.
- **The embed runtime drives the site's own modules.** The card is the site's `wizard/wizard.js` without browser history (`history: null`, `win: null`: it never touches the host's), with the steps Firmware, Setup (only with two or more `[[setup]]`), Build and Flash; a `[prebuilt]` board has Firmware and Flash, and loads no build module, no Python and no compiler: its file comes from `inline.prebuilt` or from beside the page. Every step change fires `webflash-relayout`. For a board built from source, `embed-build.js`'s `FirmwareFlow` holds the TOML's tables in a `Session` (`state.js`), loads versions with the `Configurator` (`latest` and `release` resolved as the site does) and builds with `builder.js`'s `runAll` inside `configurator.exclusive()`, Katapult first, so a card builds what the site builds. Page 1 shows the board, the firmware switch (`[firmware] projects`, plus None when the TOML has `[katapult]`; hidden with one choice or `show_versions = false`), the version pickers, the Katapult checkbox (ticked by `[katapult] default`), and with one setup the reader's options (a `values` list; the defconfig's value, else "Default"; an option without `values` is read-only behind a Change button, since only the Kconfig knows what fits). Nothing heavy loads before the reader asks: Next on page 1 is the consent (its hint names the downloads and their size), and starts Python, the sources and the compiler; a Change before it starts the same downloads without moving. Only the version list may come first: the index, and the older commits' list (`history/<project>.json`, about 40 KB gzipped) when the TOML pins an older commit or a picker opens. The Setup step is one radio card per setup with its options; a setup without a Katapult defconfig is disabled while Katapult is ticked. The reader's picks become tables through `embed-model.js`'s `cardTables` (Katapult unticked: no setup has a Katapult defconfig; None: each setup's Katapult defconfig becomes its defconfig, `project = "katapult"`), and the choices are kept per setup and set through `kconfig_set` after every load (in passes, in the TOML's order, until a pass sets nothing, so a choice shown by a later one is kept; the ones still hidden are logged as not applied). While Katapult is ticked beside a firmware, an exposed Klipper bootloader-offset option is disabled ("Set by Katapult."), since the engine links it; with None it is neither offered, applied nor written into the link (a pick made for the firmware waits for it), since Katapult's Kconfig reads those `*_FLASH_START_*` symbols as its deployer's address (`embed-model.js`'s `optionsFor` with the picks). Build starts on arrival from a step before it unless the builds still match (Back from Flash starts nothing); the flash panel (`createFlashPanel`, compact) gets `firmwareFromPair` for a pair, else `embed-model.js`'s `firmwareFromBuild` with the setup's methods (else `[flash]`'s), and lets it go while the settings differ from the build. "Open in WebFlash" carries the page's own `toml` until the reader changes something, then a TOML written from `cardTables(..., {link: true})`: the reader's setup first, with their choices in its defconfig, their project and versions (a pinned version a `versions` list lacks joins it, as on the site; a commit the list names in another abbreviation keeps the list's spelling), and Katapult as picked (a string option's value stays quoted: one the defconfig quotes, or one whose offered values no bool, int or hex symbol takes). `?mock=<kind>` on a generated page runs the flash panel against `js/flash/mocks/`, as on the site.
- **Embedding from another origin needs `allow="usb; serial"`.** A page beside the Markdown (the docs site's own origin) needs nothing. Served from another origin, the iframe needs `allow="usb; serial"` (md-iframe keeps the attribute: `![Flash](https://example.org/board.webflash.html){ type=iframe allow="usb; serial" }`); without it the browser refuses both pickers ("disallowed by permissions policy"), and the card says so, still builds and offers the files and a link to open the card in its own tab; a frame that allows only one of the two APIs keeps the methods on that API, and the notice names what it withholds (`embed-model.js`'s `frameNotice`). Even with it, browsers open no folder picker in a frame from another origin, so the UF2 drive is a `.uf2` download there (`errors.js`'s `capabilities().crossOriginFrame`).
- **Where the toolchain and the sources come from.** `index.html` carries a `<!--webflash-assets-->` placeholder that the local server replaces with `<meta name="webflash-assets" content="<url>">`: the `--assets` URL (default `https://webflash.isiks.tech/`), or empty for an `--assets` folder, which the server then serves at `/toolchain/` and `/sources/`. The hosted site ships the placeholder untouched, so there is no tag and the page uses its own origin. `runtime.assetsBase()` reads it.
- **The board TOML is strict, themes are lenient.** Unknown keys and tables in a board TOML are errors, and so are wrong types, unknown projects and methods, a `[firmware]` / `[config]` / `[prebuilt]` mix, a defconfig line that is not `.config` syntax as kconfiglib reads it (an indented line, or an unset line not written `# CONFIG_X is not set`), sets a symbol twice or holds a decimal number with a leading zero (C would read it as octal), a `.bin` without `address` and any other file with one. A firmware's configuration is `[config]` (`defconfig`, optionally `katapult`, Katapult's defconfig: one setup with id `default`) or repeated `[[setup]]` tables (`id`, `[a-z0-9-]+` and unique; `title`, required; `description`; `defconfig`; `katapult`; `methods`, as `[flash] methods`), never both; `[katapult]` (`version`, `versions`, `default`, a bool for whether the card opens with Katapult ticked) needs a firmware other than Katapult and at least one setup with a `katapult` defconfig, and a `katapult` key without `[katapult]` is an error; `[[option]] setups` names existing setup ids (default: all). `board_data` gives `setups` (a list) and `setups_form` (`"config"` or `"setup"`) for both shapes, and the writers write `[config]` back only while the one setup holds nothing only `[[setup]]` can. `[board] image` is a URL (a scheme such as `https:` or `data:`, or `//host/...`) or a path relative to the TOML without `..`, a drive or a leading `/`; `[prebuilt] file` is such a relative path, never a URL; `webflash -i` and the bridge read only files below the TOML's folder. Errors read `<file>: <table>: <message>`. Warnings (a label for a value not offered, instructions for a method not offered) are collected on `BoardConfig.warnings`. The loader never checks symbols against a Kconfig or versions against the sources index: the site does that once it has them. - **Two TOML writers write the same text.** `config.dump_board` (behind `bridge.save_toml`) and `toml-io.js`'s `writeBoardToml` write a fresh board TOML from `board_data`'s tables, in the order of the board TOML reference (`[board]`, `[firmware]`, `[katapult]`, `[config]` or each `[[setup]]`, `[[option]]`, `[flash]`, `[prebuilt]`), leaving out keys that hold their default (except `[firmware] version` and `[katapult] version`). - **Configuring a version.** `sources/index.json` (from the assets origin, revalidated) lists each project's refs: the default branch, tags newest first, other branches. A project with older commits names their file (`history: {file, count}`): `sources/history/<project>.json` (`{schema, project, refs, blobs}`) lists the first-parent commits of the default branch from the policy's window, newest first, each under its `git describe` string as `id` (`kind: "commit"`, `sha`, `date`, its bundles, `checked`), with its own `blobs` table; it loads only when a picker opens or a version names an older commit (never for a picker whose `versions` cannot hold one, such as `releases` or a list of tags: `version-picker.js`'s `mayOfferOlder`) (`sources.js`'s `loadHistory`, cached per index object; `resolveVersionAsync`). `[firmware] version` and `[katapult] version` are `latest` (the default branch's snapshot when its `checked` is true, else the newest checked ref, else the default branch, badged), `release` (the newest checked tag), a ref id or an older commit's describe string; a ref whose `checked` is false or null is badged "unchecked" and never chosen by those two. Every version control is `version-picker.js`'s `mountVersionPicker(el, {project, index, value, versions, onChange, base?, disabled?, label?})`, a combobox (groups Latest, Releases, Branches, Older commits; at most 50 older commits shown until the user types): typing filters, and a pasted Mainsail or Fluidd version (`v0.13.0-245-g61c0c8d`, `-dirty` or not, or a bare hash; an MCU version's build stamp, `-<YYYYMMDD_HHMMSS>-<host>`, is ignored with a note) picks that commit when it is kept, else the closest older kept commit on the same tag, with "Closest kept: …" under the control, naming the branch when it is another branch's head, since a describe string names none (`sources.js`'s `findVersion`), and anything but the commit itself waits for the older commits (Enter and a paste wait while they load; when they fail, the open list shows why with Try again); a picker whose `versions` narrows the list (a card's) matches only among the versions offered, with "Closest offered: …", and holds `latest` or `release` for the ref it names when the list offers that and not the ref (`version-picker.js`'s `matchVersion`). The Configure step loads the chosen ref's core bundle (later visits load at once from the cache), runs `kconfig_load` with the setup's defconfig, and renders `kconfig_tree()` (the engine's `{root: [ids], nodes, title}`, normalized by `kconfig-tree.js`'s `normalizeTree`) as menuconfig shows it, patched by node id after each `kconfig_set`; menus start folded (`localStorage` `webflash.kconfig.folds.<project>` remembers what the user opened or closed), groups never, and a search opens its matches. Switching project or version carries the defconfig over, plus the selected `MACH_` architecture and processor where the defconfig leaves them to the defaults (the projects default to different chips), and lists the symbols the new version lacks and the values it would not take; a fresh firmware configuration gets `CONFIG_LOW_LEVEL_OPTIONS=y` (`STARTER_DEFCONFIG`, and a project switch whose defconfig does not name it). Reset loads every default but the chip and the low-level options. Every engine call runs in order through `configurator.js`'s queue (`load`, `apply` or `reapply` inside `exclusive()` would wait behind it for good); `reapply` (undo, redo, another setup picked) follows a load of the same project and version still in flight and supersedes one of another, so an undo during an opened TOML's download brings the engine back to the restored board. A bundle that answers 404 (an old snapshot of a moved branch) makes the page reload the index once.
- **Two engine slots: a firmware and Katapult, paired.** The engine holds up to two configurations, keyed by slot: `"fw"` (Klipper, Kalico, or Katapult when it is picked alone) and `"katapult"` (Katapult beside a firmware). `bridge.py`'s Kconfig, plan and build functions take the slot first (`load_sources(slot, project, ref_json, core_bytes)`, `kconfig_load`, `kconfig_tree`, `kconfig_set`, `kconfig_config`, `kconfig_defconfig`, `kconfig_symbol`, `kconfig_search`, `plan`, `add_lib`, `build`, `build_output`, `infer_methods`; `drop_slot(slot)`), `runtime.js`'s wrappers take `{slot = "fw"}`, and node ids are prefixed with their slot (`fw:n12`, `katapult:n4`). A slot's tree is extracted at `/webflash/src/<project>/<sha>`; one the other slot shares is extracted over, never wiped. Paired (both loaded, `fw` not Katapult), `engine/pair.py` finds the shared options (symbols and choices both trees define with the same type and a prompt in both, minus a deny list: `LOW_LEVEL_OPTIONS`, `INITIAL_PINS`, `USB_DEVICE_ID`, `FLASH_APPLICATION_ADDRESS` and the `*_FLASH_START_*` choices; a firmware interface member Katapult lacks falls back to its `USB` name, so a USB to CAN bridge runs Katapult as plain USB; the RP2040 names of Klipper v0.12.0 and older and of Katapult before RP2350 support, `MACH_RP2040` and `RP2040_*`, are read as `MACH_RPXXXX` and `RPXXXX_*`, so either layout pairs with either): `kconfig_set` on one mirrors it into the other, with a note when the other refuses the value ("Katapult has no …"), and Klipper's bootloader offset follows Katapult's application offset (STM32 `STM32_APP_START_X` → `STM32_FLASH_START_X`; RP2040/RP2350 and LPC176x 16 KiB), locked in Klipper (`locked: "katapult"`), with an error when Klipper has no such offset for the chip. `pair_tree()` gives the Configure step its three groups ("Board · used by both", "Klipper only", "Katapult only"); `pair_sync(source)` copies the shared options from one slot into the other and links: from `fw` after a version loads (`_configure`, `reapply`), from the loaded slot after Configure's Load .config (`apply`), so a .config loaded into Katapult stands; its answer's `copied` names the options the other slot showed before and after whose value changed, which a Katapult .config opened beside the firmware's (Open .config, reason `config`) reports as what the firmware's won over. The `Configurator` keeps `slots = {fw, katapult}`, `paired`, `loadKatapult()`, `dropKatapult()` and one queue for both; `session.katapult` (null, or `{on, version, defconfigText, ref, configText, tree, plan, sources, link, notes}`) is the selected setup's Katapult part, with `version` and `defconfigText` read from the tables.
- **The build runs in toolchain workers.** Build reads `toolchain/current.json` (revalidated) and `toolchain/<id>/manifest.json`, loads the release's `llvm.js`, `llvm.wasm.gz`, `toolchain.js` and `sysroot.tar.gz` through Cache Storage, each checked against the manifest's size and SHA-256 (a copy that fails is dropped and fetched again), and starts N `workers/toolchain-worker.js` module workers: one per core but one, at most 4, halved below 8 GB of `navigator.deviceMemory`, or what About sets (`localStorage` `webflash.build.workers`). Each worker gets the bytes, imports `toolchain.js` and `llvm.js` from Blob URLs of them (so a repeat visit fetches nothing; Node falls back to the files' URLs), compiles the module once, and mounts the core and lib bundles at the engine's own tree path (`/webflash/src/<project>/<sha>`). The page hands one `MessagePort` per worker to the engine worker (`attachToolchain`), whose `webflash_js.run_tool(spec_json, files)` (the engine's `JsToolchain` hook) queues each job for the next free worker, the job's files transferred; a worker runs one job at a time, creates the folders the outputs go to (the tools create none; MEMFS resolves `..` from the folder it has reached, so `out/src/../lib/x.o` needs `out/src` too) and answers every file the tool wrote. The build runs inside `configurator.exclusive()` with configuring locked; Cancel aborts the call, fails the queued jobs (`detachToolchain`) and terminates the workers, which start again with the next build; a Cancel during the compiler's or a bundle's download, or while a card loads its configuration, ends the build at once, and the download (or the load) finishes in the background, so the cache and the engine stay whole. Next on page 1 (the site's and a card's) is the consent to download, so the compiler arrives while the user configures and the first Build asks nothing more (`buildPanel.consented`, `prefetch()`); `Builder.fetchToolchain` is that one download, and `prepare()` joins it when Build comes first. Configure's start box (shown when Configure is reached without page 1's Next) offers the same with a checkbox. A Build nothing agreed to (after Clear cache, say) lists the downloads with sizes (the sources too, when the compiler workers lack the tree) and waits for a click (`localStorage` `webflash.build.auto` once the release is in Cache Storage). A pair is `Builder.runAll(jobs, {step, onProgress, onStart, onDone, signal})`: one job per slot, Katapult first, under one `exclusive()` with the compiler workers kept (the pool remounts each tree); a Cancel between jobs ends the run with `BuildCancelled`, and the builds that finished are kept. A build, Rebuild included, builds every slot again, Katapult and the firmware, even when only one of them changed. "Built in" is the whole wait the running clock showed, downloads included; its tooltip and the log give the compile time. The result goes to `session.builds` (`{fw, katapult}`, each `{slot, project, ref, version, config, outputs: Map, appAddress, mcu, ...}`; `appAddress` is `CONFIG_FLASH_START` for Katapult; `session.build` is `builds.fw`) with a `change` event `"build"`. The Build step shows one row per slot (status, a bar, the files as chips), the prerequisites in one line, and Memory and Log folded. The Flash step, like a card, offers the builds only while each slot's project, ref and `.config` are its build's (`artifacts.js`'s `buildMatches(session, build, slot)` and `buildsMatch`, which Rebuild also uses); opening a board TOML clears `session.builds` (the Build step keeps its files, marked as from an earlier configuration), and a `[prebuilt]` TOML's card always flashes the TOML's own file. The Memory table's flash row counts the image as loaded (by load address, from the link's ELF and `-T` script), since lld's `--print-memory-usage` counts run addresses and the RP2040/RP2350 run their code from RAM; a corrected region keeps lld's figure as `linker`. A Katapult build's flash row is measured against Katapult's own space, `CONFIG_LAUNCH_APP_ADDRESS` minus `CONFIG_FLASH_START` (8 KiB for `STM32_APP_START_2000`), since its linker script's region is the whole flash and only `buildbinary.py` enforces the limit; the row keeps the region's length as `region_size`, and its tooltip says so. The browser's build is byte-identical to the same WebAssembly module run under Node (`webflash build --toolchain wasm-node`, see below), so a firmware the site built can be reproduced exactly.
- **Arm only.** WebFlash builds firmware for Arm chips only (STM32, RP2040/RP2350, LPC176x, SAM/SAMD, HC32F460). A configuration whose architecture is Atmega AVR, Beaglebone PRU, Allwinner AR100, Linux process or Host simulator is refused before the plan with one sentence (`engine/methods.py`'s `unsupported_reason`, the twin of `devices.js`'s `unsupportedReason`): `Build` raises it, `bridge.plan` raises it, and the Build step and a card's `blockReason()` show it. Klipper's Reset to defaults lands on AVR. In clang mode the driver also refuses the host's gcc/cc and other targets' cross tools (bare `cpp` stays, for the linker scripts).
- **Flashing.** `devices.js` `inferMethods` (and its Python twin `engine/methods.py`) reads the resolved `.config`: Katapult first when there is a bootloader offset (over CAN for a CAN build; over Web Serial for a USB or UART build and for a USB to CAN bridge, which runs Katapult on its own USB port), then the chip's ROM method (DFU on an STM32 whose ROM has USB DFU, PICOBOOT and the UF2 drive on an RP2040 or RP2350), then Download; the board TOML's `[flash] methods` (or the setup's own `methods`) narrows and orders that. Katapult and a firmware built together are one firmware object (`flash/pair.js`'s `firmwareFromPair`, also the card's): an image of two segments, Katapult at its `FLASH_START` and the firmware at its application address, refused with a sentence when Katapult runs past that address; its methods are the ROM methods both allow, which write both in one session (DFU and PICOBOOT write any number of segments; the UF2 drive gets one `.uf2` encoded from both segments, never two files joined), then Katapult's own methods, which write the firmware alone ("Klipper only", with a note that Katapult must be on the board already and how to put it there: the ROM method once, else `deployer.bin` copied to the SD card as `firmware.bin`, else an SWD or ISP tool; a pair without a ROM method, an LPC176x's, has Download steps that say the same), then Download. The Flash step lists the writes from the image's segments, labeled by project. Katapult in UART mode (a firmware whose interface is serial) is opened at `CONFIG_SERIAL_BAUD`, from the `.config` or an uploaded file's dictionary, else 250000 (`devices.js`'s `serialBaud`); its Connect lists every serial port, since a USB-UART adapter has no Katapult id, and its restart from Klipper is the serial bootloader request (`bootloader-entry.js`'s `enterFromKlipperSerial`) on the adapter's port, not the 1200-baud touch. Katapult over CAN clears the node ids before the first query, as flashtool does, so a node left with an id by a broken-off attempt is found again; a node that does not answer the query (Klipper under a host) is flashed by its `canbus_uuid`, typed in the folded field under the node list (open when no node answered), which sends the bootloader request to that UUID, and with no node and no UUID the error says to stop Klipper on the host. Whether the ROM has DFU comes from the chip: `CONFIG_STM32_DFU_ROM_ADDRESS` is 0 for every build without USB (Klipper's rule for restarting itself into the ROM), yet a CAN toolhead with a USB port is flashed through the ROM's DFU like any board, so a 0 there falls back to the Kconfig's table (F042, F072, F4, F7, G0 except the G070/G071, G4, L4, H7). An uploaded Klipper file's dictionary (MCU, reserved pins, CAN bitrate) becomes a configuration of its own, so a file decides its own methods. The printer.cfg hint follows the firmware's interface (`canbus_uuid` for CAN nodes and bridges) and says `<serial>` with how to find it where nothing tells Klipper's serial: Web Serial gives no serial number, and the ST ROM's and the RP2040 BOOTSEL ROM's serials are not the chip id Klipper reports. A lost device is a `FlashError` coded `disconnected` (a BOOTSEL drive that goes away before the last chunk of the `.uf2` was handed over is one too, since the ROM restarts only once it has every block: only an error on the last chunk or on `close()` counts as the board restarting, and a refusal never does), and `errors.js`'s `explainError` turns every error into a title, a message and fixes for the OS and browser. On Windows the ROM bootloaders need the WinUSB driver once (Zadig: "DFU in FS Mode" or "STM32 BOOTLOADER", "RP2 Boot (Interface 1)"); Katapult over USB and candleLight adapters need nothing. Brave ships with the File System Access API off (the UF2 drive becomes a download unless `brave://flags/#file-system-access-api` is on) and hands pages made-up USB serial numbers. An RP2040 board with an IS25LP flash chip (a KUSBA) boots Klipper only with "Flash chip: GENERIC_03H with CLKDIV 4" under the low-level options. `?mock=<kind>[&fail=...]` (`dfu`, `katapult`, `uart`, `can`, `picoboot`, `uf2`; `uf2` takes `&fail=vanish`, a restart inside the last chunk, and `&fail=unplug`, a cable pulled; `can` has a node a host holds, `112233445566`, and `&bus=host` leaves only it) runs the panel against `js/flash/mocks/`.
- **The Flash step's rules.** While a device is being picked or written, the Method select is locked and a new firmware (a Kconfig change mid-flash) waits until the flash ends, keeping the result; a connection the card drops, or replaces with another pick, is closed. An uploaded file is what the Flash step offers until a build finishes after it, which takes its place (uploading again brings the file back). Upload firmware decides the format by content (a HEX under any name; a text file such as `klipper.dict` is refused), and the raw `.bin` address prompt reads hex with or without `0x`. Klipper's elf2uf2 stamps the RP2040 family id on every RP2 build; the engine writes the RP2350 (Arm, secure) family for a `CONFIG_MACH_RP2350` build (`uf2.family_for_config`), the Flash step treats an uploaded RP2040-family UF2 whose first 4 KiB hold a picobin `IMAGE_DEF` as an RP2350 image (`firmware-file.js`'s `rp2350FamilyOfImage`, `image.stampedFamily`) and encodes it again for the RP2350 drive, and a UF2 for another chip family is only offered as a download. A DFU bootloader that stays busy for over 30 s (`dfu.js`'s `DFU_SETTLE_MS`) fails the flash with a `timeout` instead of polling forever, and a serial framing, parity, break or overrun error reopens the reader instead of ending the flash (more than 20 within 2 s fail it). Katapult's COMPLETE (which starts the application unchecked) goes out only after the whole image was written, even when the verification then fails; a write that breaks off on a block leaves the board in Katapult, and its error says to connect again and click Flash. The address prompt of a raw `.bin` upload refuses while a device is being picked or written (a `FlashError` coded `busy`), since it shares its box with the CAN node list; an upload's error names the file once. The progress line counts erased pages and sectors and verified blocks as counts (the `progress` callback's fourth argument, `unit`), bytes for writes. "Restart Klipper into the bootloader" under DFU and PICOBOOT (the USB 1200-baud touch) is offered only for a firmware whose Klipper runs a USB CDC port (interface `usb`, or unknown), not for a UART, CAN or USB-to-CAN bridge build, which the touch cannot reach. A UART build's printer.cfg hint names `baud:` when it is not Klipper's default 250000.
- **GitHub Pages and the caches.** Pages sends `access-control-allow-origin: *` and `cache-control: max-age=600` on everything, and compresses `.gz` files again in transit, so `Content-Length` is the wire size: download totals come from the index's `blobs` table and the toolchain manifest. A deploy reaches a returning visitor's page code within ten minutes; the toolchain and the bundles never change under their URLs, and Cache Storage keeps them. A download that breaks off names the file and how far it got, and nothing of it is kept.
- **The snapshot gate.** `webflash sources build` makes a full clone of each project (the `git describe` string needs the history), bundles every ref the policy names, and gates each new snapshot: for every matrix row whose symbols the tree defines, `webflash make-check` against real `make -n V=1` and `webflash build --toolchain gcc` on a tree extracted from the bundles. A failure publishes the ref with `checked: false` and exits 2. Older commits are gated once per distinct bundle set (a snapshot whose bundles equal a gated one's takes its report, marked `same_as`; most commits change only `klippy/`, docs or config, which no bundle holds), newest first across projects, until `--gate-minutes` runs out; the rest are published with `checked: null` and the next run carries on (`pages.yml` gives it 90 minutes a day by default; the first backfill is about 3 hours in all). With the starting policy, about 800 older commits add about 123 MB to `sources/`. Klipper `v0.12.0` and `v0.11.0` fail on purpose (their Cortex-M3/M4/M7 rows cannot link with a current GCC, an upstream bug fixed after `v0.12.0`) and stay listed, unchecked, because the browser's clang builds them. Those clang builds carry an orphan `.ARM.exidx` section (16 bytes; their `armcm_link.lds.S` has no rule for it) that lld places itself, in flash after `.text` or, on the SAME70, in RAM between `.data` and `.bss`: benign (the startup's symbols bracket it), and left as is, since WebFlash links each tree with its own script. Their RP2040 layout (`MACH_RP2040`, with elf2uf2 under `lib/rp2040/`, which the core bundle keeps) is gated by the matrix row `rp2040-usb-legacy`, whose `unless = ["MACH_RPXXXX"]` makes it apply only to trees without the newer symbol; `make-check` and `parity` print such a row as skipped. The maintainer commands refuse a source tree whose path has a space (the Makefiles put `$(CURDIR)` in make targets). On Windows run it with GNU make and the Arm GNU Toolchain's `bin` on `PATH` and with `TEMP`, `--cache` and `--clones` under a short path: that toolchain cannot open a path over 260 characters, and the RP2040 rows' stage-2 includes are long. From an empty cache it takes about 6 minutes on a 32-core machine.
- **The payload holds `bridge.py` at its root and the package under `webflash/`**: every `.py` and `.toml` except the site and the server-side modules (`cli.py`, `serve.py`, `payload.py`, `sources.py`, `__main__.py`). The zip's comment is a digest of every member's name and bytes, and `payload_is_stale` compares it rather than mtimes. It is built beside the site in a source checkout and in the per-user cache (`<cache>/webflash/<hash of the package path>/`) for an installed package, exactly as PinConnect's. A running `webflash` rebuilds a stale payload when the site asks for it, under one lock, served from memory; only an edit to `serve.py` or `payload.py` needs a restart.
- **Package data is listed by file type** in `pyproject.toml` (`site/js/*.js`, `site/js/*/*.js` and so on), not with a recursive glob: older setuptools releases do not expand `**`, and the explicit list keeps the payload zip and bytecode caches out of the wheel. A new kind of file (a new folder depth or extension, such as `.wasm` or `.mjs`) needs a line there.

## Common commands

Install for development and run the site (Python 3.9+):

```bash
pip install -e .
webflash                       # builds the payload, picks a port, opens a browser
webflash --port 8000 --no-browser
webflash --assets ./local-assets   # serve toolchain/ and sources/ from a folder
```

Render a board TOML:

```bash
webflash examples/stm32g0b1-usb/stm32g0b1-usb.toml          # writes examples/stm32g0b1-usb/stm32g0b1-usb.webflash.html
webflash examples/can-toolhead/can-toolhead.toml -t slate -i -o can.html
```

Build the site's payload by hand (only needed to serve `src/webflash/site/` some other way):

```bash
python -m webflash.payload --force
```

The maintainer commands run the build engine natively (GNU make, and `arm-none-eabi-gcc` or ATfE's clang, on `PATH` or named with `--toolchain-dir`; a tree is a project checkout or one extracted from the bundles):

```bash
webflash sources build --policy sources.toml --out _site/sources --cache <cache> --clones <clones>   # snapshots and the gate
webflash sources build ... --gate-minutes 200                   # gate more older commits in one run (--no-history leaves them as recorded)
webflash sources check --out _site/sources                     # the written folder against the index contract
webflash make-check <tree> --row stm32g0b1-usb --project klipper   # the interpreter against make -n V=1
webflash build <tree> --config row.config --toolchain gcc -j 4 --out out
webflash build <tree> --config row.config --toolchain wasm-node --toolchain-dir <release> --wasm-mount /webflash/src/klipper/<sha>
webflash parity <tree> --row stm32g0b1-usb --toolchains gcc,clang-native,wasm-node --wasm-dir <release>
webflash inspect out/klipper.elf                                # sizes, vector table, segments
```

## Parity and hardware

- **`tools/parity/matrix.toml`** holds one row per MCU family and flashing path; `ci.yml` runs `make-check` and `parity` over all of it on Ubuntu, and the snapshot gate builds every row that applies to a new snapshot. clang's code is larger than GCC's (up to about 45% on the Cortex-M3/M4/M7 rows with LTO; every row fits its region), and the two number the dictionary's messages in a different order, so `parity` compares dictionaries by their message sets, not byte for byte. Every clang line is soft-float (`-mfloat-abi=soft`, GCC's default, and `-plugin-opt=-mattr=-fpregs` on LTO links for a CPU with an FPU), since the projects never enable the FPU; `parity` fails a row whose ELF has a `Tag_FP_arch` attribute or FPU instructions (counted with GNU objdump from `--gcc-dir` or `PATH`) that the GCC build lacks. The clang links name `--entry=ResetHandler`, since the scripts name no `ENTRY` and lld would otherwise warn on every link; `.bin`, `.hex` and `.uf2` do not depend on it.
- **The browser's build can be reproduced exactly**: `webflash build --toolchain wasm-node --toolchain-dir <unpacked toolchain release> --wasm-mount /webflash/src/<project>/<sha>` runs the same WebAssembly module under Node with the tree where the site mounts it, and gives the same bytes (the mount is the compilation directory the ELF's debug information records).
- **`tools/parity/hardware.md`** is the checklist for real boards: how to run a row, the STOP sessions so far, and a table of every result with the date, OS and browser. A change to `site/js/flash/` is first run against the mocks (`?mock=`), then on a board, and the result goes into that table.

## Documentation

The docs will live in [doctools-docs](https://github.com/xbst/doctools-docs) (a sibling checkout, `..\doctools-docs`), the Zensical site shared with PinConnect, 3DStep and md-iframe, under `docs/webflash/`. Topics shared by every tool (publishing from CI, light and dark mode) are under its `docs/guides/`.

- **A behavior change here usually needs a docs change there.** Make it in doctools-docs in step with the code change, as a commit in that repository, and mention it in this one's commit message. The board TOML and theme references follow `config.py`; the generated page's reference follows `renderer.py` and the embed runtime; the command line page follows `cli.py`.

## Conventions

- **Docs use one line per paragraph.** GitHub's Markdown viewer soft-wraps, so do not hard-wrap prose in the README, this file or doctools-docs.
- **Code, comments and docs are US English.** Prose uses `colors`, `behaviors`, `gray`, `labeled`, matching the TOML keys users type.
- **Commit messages** are a short imperative sentence ("Add the Kconfig tree", "Fix the DFU erase loop"), no conventional-commit prefixes.
- **Generated and ephemeral files are git-ignored** through a local-only `.gitignore` (it ignores itself, as in PinConnect and 3DStep, so a fresh clone or worktree has none: copy it in). Never commit `*.webflash.html`, `src/webflash/site/webflash.zip`, `tests/`, `plans/`, `venv/` or `.claude/`.
- **No new runtime dependencies without reason.** `webflash` relies only on the standard library (`tomllib`, with a `tomli` fallback below 3.11); the site is dependency-free vanilla JS at runtime apart from Pyodide from a CDN and the toolchain release.

## Verifying changes

- After editing `renderer.py`, `config.py`, a theme or `site/js/embed/`, render the examples with `engine_url = "http://127.0.0.1:<port>/engine/v1/"` (a running `webflash --port <port> --assets <folder or URL>`) and open the HTML over HTTP (`python -m http.server` in a folder holding the page and its photo), standalone and in light and dark (`?theme=dark`), at 1280 and 375 px, then inside a scratch Zensical site with md-iframe (the toggle; the height on every step and as the build's results and the log open and close; `examples/can-toolhead` for the Setup step, both setups). The console should stay clean. Until the site is deployed, a page with the default `engine_url` logs one failed load, of `embed.js` from `webflash.isiks.tech`.
- After editing anything in the package (a theme, the bridge, the renderer), reload the site (a running `webflash` rebuilds its payload; restart it only after changing `serve.py` or `payload.py`) and confirm Generate still works. An example's Generate in the site must give the same bytes as `webflash` on the same TOML, with and without `-i`.
- After changing packaging, build a wheel (`python -m build`) and list it: it should hold exactly `webflash/**` plus metadata, with no zip and no tests.
- To test the hosted layout before a deploy, stage `_site/` as `pages.yml`'s build job does (its "Stage the site" step, an unpacked toolchain release under `toolchain/<id>/` with `current.json`, and a `webflash sources build` output under `sources/`), run its "Check the site" script and `webflash sources check`, and serve the folder with headers like GitHub Pages' (`access-control-allow-origin: *`, `cache-control: max-age=600`, `.gz` files gzipped again in transit). A page's modules then stay in the browser's HTTP cache for ten minutes: reload with the cache bypassed after staging again.
- After editing `site/js/flash/`, run the Flash step against the mocks (`?mock=dfu`, `katapult`, `uart`, `can`, `picoboot`, `uf2`, with `&fail=` for the error paths) in light and dark, with one firmware and with Katapult and Klipper together, then run the affected rows of `tools/parity/hardware.md` on a board.
- **Tests are not committed** (`tests/` and `test_*.py` are git-ignored), so a fresh clone has none. A working copy may still have `tests/`: if they are present, run `python -m pytest tests` and `node --no-warnings --test "tests/js/*.test.mjs" "tests/js/flash/*.test.mjs"` (Node 24 does not expand a bare directory) before finishing, and add cases for new behavior. Never `git add` a test file.
